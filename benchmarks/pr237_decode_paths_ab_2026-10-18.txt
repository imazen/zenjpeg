Interpretation by changed code path
-----------------------------------

dct16 / w16 IDCT (the specific ask):
  The AVX2 w16 pmaddwd-i16 kernel is unchanged on the clamped u8 path
  (idct_int_libjpeg_streaming_avx2_w16 still serves it; dense clamped tiered
  actually measured 27->24ns, likely code-layout noise). The real change is on
  the UNCLAMPED (f32-target) Libjpeg path: before dispatched to
  idct_int_libjpeg_avx2_w16_d32(.., clamp=false), whose raw i16 store skipped
  the +128 level shift and the +-UNCLAMPED_SAMPLE_LIMIT bound — wrong output.
  After dispatches to idct_int_libjpeg_auto_unclamped (guarded i32 AVX2 or
  scalar). Kernel-level cost: 3.4x on all-64-coeff blocks (25->85ns), 1.7x on
  sparse 8-coeff blocks (23->39ns), 0x on DC-only blocks (both early-out to
  idct_int_dc_only_unclamped, 5ns). End-to-end zen-f32 is parity on every
  fixture (0.99-1.00x): real q85 photo blocks are mostly DC/sparse and the f32
  path is dominated by per-pixel f32 colour conversion (~10x the u8 cost), so
  the IDCT delta is under ~1% of wall time. Conclusion: a correctness fix with
  a real kernel-level cost (up to +60ns/block on dense blocks) that is
  invisible at image level on normal content. An all-dense-AC f32 decode would
  show more; not measured here (no such fixture).

DC-only tiered dispatch (S4, 05ca465a):
  DC-only blocks in strip/fused paths now dequantize into dequant_buf and call
  the configured tiered IDCT with coeff_count==1 instead of a direct
  idct_int_dc_only splat. Micro-bench: 5->5-6ns/block (~1ns dispatch overhead).
  End-to-end on the DC-heavy fixture (nearly all blocks DC-only): +2.3% on
  2048px, +0.3% on 768px; on normal content ~+1% (indistinguishable from the
  ambient +1-1.5% drift seen on zen-tri/zen-seq across all fixtures).

4:2:2 nearest (row-kernel routing win):
  0.748x on both sizes — the C1 fast-integer row path now upsamples h2 chroma
  from half-width rows instead of the old full-width route. Largest single win
  in the diff for ordinary decode.

RGB-coded 4:4:4 (rgb444):
  0.85-0.90x across RGB/BGR/jpegli lanes (and BGR is now correct — before
  returned unswapped data on this fixture too). The RowKernel/fused gating
  avoids running YCbCr matrix work on RGB-coded frames.

4:4:0 (H1V2):
  decode() regresses ~+5.5-6.7% on the DRI variant and +1.6-3.4% sequential on
  non-DRI 440 (PathPlan excludes H1V2 from the fused/parallel MCU kernels that
  output_parallel.rs used to serve). Wave-parallel probes (zen-planar,
  zen-wave on 440dri) show parity ~0.99-1.00x: wave never actually engaged
  for this shape on either rev (planar ~= seq both sides), so the measured
  regression is the streaming/strip path, not lost threading. 4:4:0 remains
  correct via the streaming h1v2 path.

Boundary4Tap deblock (KB5, 634b41e1):
  zen-scan-db roughly doubles on 420/440/dcheavy fixtures (1.8x-2.5x) and grows
  +28-43% on progressive/rgb444. This is a correctness expansion: on main,
  Boundary4Tap on the scanline path was effectively a no-op for these shapes
  (scan-db ~= scan before: 10.03 vs 10.01ms on big-420); after, deblock runs
  on preloaded + coefficient MCU rows as documented, so the scanline-deblock
  path now does real work it silently skipped before. 444/progressive already
  paid that cost on main (33ms scan-db there) and are unchanged-to-better.

Baseline/progressive parity:
  Ordinary 420/444 decode is within ~1-2% (zen-tri +1.0-1.6%, ambient moz lanes
  hold ~1.00x). Progressive is slightly faster (0.98-0.99x) plus correct BGR.
  fast_integer threaded path (420p zen-par 13.7->13.5ms, 1.3x over seq) is
  parity. No fused/wave path showed a measurable change.

Net: no ordinary-decode regressions beyond ~1-2% except 4:4:0 (~+3-7%) and the
correctness-priced lanes (BGR swap where it was previously skipped, real
deblock coverage). Real wins: 4:2:2-nearest -25%, RGB-coded -10-15%,
progressive -1-2%. The w16->i32 unclamped switch costs 1.7-3.4x per non-DC
block at kernel level and ~0% at image level on this corpus.
